title: Release process
description: Prepare, validate, publish, and audit a Satelle release.
---

Satelle releases start with a reviewed release pull request and finish only
after the tag workflow validates the whole binary and npm package graph. A
pull request merge never publishes packages or creates a final GitHub release.

## Release tooling boundaries

[Tegami](https://tegami.fuma-nama.dev/getting-started) 1.2.5 is the preferred
changelog and versioning tool. It runs on Node.js 24 as isolated repository
tooling under `npm/release-tooling`; neither Tegami nor Node.js is a runtime
dependency of the Rust CLI or Host Daemon.

Run the non-mutating validation before preparing a release:

```sh
npm ci --prefix npm/release-tooling --ignore-scripts
npm run dry-run --prefix npm/release-tooling
```

The report records the Node.js and Tegami versions, discovery of the single
`satelle` Cargo package, the temporary fixture's generated files, version and
dependency updates, and the registry targets skipped by the dry run. Tegami
owns changelog and version planning. It does not publish the Cargo package.

On the normal path, the release workflow runs Tegami's publication plan after
the dry run passes. `release.yml` is the explicit publication hook for native
binaries, the Cargo package, and the npm graph. This keeps registry writes out
of Tegami without bypassing its changelog and version plan.

## Cargo package contract

The workspace contains one publishable Cargo package named `satelle`.
`cargo install satelle` installs its only supported public surface, the
`satelle` executable. The package keeps the core, Host, and transport module
boundaries in one source tree and has no path or Git dependency on an internal
Satelle crate. Its Rust modules are implementation details and do not promise a
stable library API.

Cargo versions match the GitHub and npm release version. Semantic versioning
applies to the executable's documented commands and machine-readable
contracts. It does not make undocumented Rust module paths stable.

The package contents are limited by its manifest to the Rust sources and
conformance tests, bundled skills and platform contract, changelog, readme, and
required third-party license notices. `cargo package --locked` builds that exact
archive during pull request validation. The signed-tag workflow publishes the
validated version and compares an existing crates.io version byte-for-byte on a
retry. A local developer command must not publish it.

The workflow checks the crates.io version metadata endpoint before publication.
A metadata 404 permits first publication; other errors stop the release. The
archive download endpoint cannot establish absence because its storage service
can return 403 for a version that does not exist. Existing versions still require
a successful archive download and an exact match with the validated package.

Crates.io ownership is limited to the release-maintainer team. Add or remove an
owner only through a reviewed repository administration change. The Actions
secret `CARGO_REGISTRY_TOKEN` holds a crates.io token scoped to publishing this
package. Do not copy it to a developer machine or reuse it for other crates.

If Tegami validation fails, the release pull request can select the manual release
fallback by adding `npm/release-tooling/manual-release.json`. The
reviewed file must use schema `satelle.manual-release-fallback.v1` and match the
release version. It must also set `generatedChangesReviewed` to `true`, give a
nonempty `reason`, and list the committed versioned Cargo `CHANGELOG.md` files.
The tag workflow validates that record and those files before it uses the same
signed artifact publication hook. Without that reviewed record, a Tegami
failure stops publication.

## Release pull request

Pull request and signed-tag release validation both check that the committed Tegami changelog describes the candidate version. A missing entry fails validation before publication.

The release pull request must contain one reviewed version everywhere the
release contract requires it: the Cargo package, all eight npm package
manifests, exact launcher dependency ranges, lockfiles, and Tegami changelog
output. At least one committed Cargo package `CHANGELOG.md` must contain a
heading for that exact version. Run the repository release checks without
publishing:

```sh
node npm/scripts/release.cjs check
npm test
```

The GitHub Actions pull request run builds all six Controller targets, packages
the crates.io archive, packs all eight npm packages, validates native binary
formats and archive roots, compares archive and npm executable digests, creates
checksums, runs registry dry runs, and exercises install, upgrade, smoke, and
uninstall paths.

## macOS distribution

Mac CLI archives and npm packages contain the same ad hoc signed executable.
CI signs and verifies both Mac architectures before packaging. This does not
require a paid Apple Developer account. These releases are not Apple-notarized
and do not carry a Developer ID publisher identity.

If macOS blocks the downloaded executable as coming from an unidentified
developer, review the release source and checksums, then use Apple's
[app-specific approval process](https://support.apple.com/en-ie/guide/mac-help/mh40616/mac)
in System Settings, Privacy & Security. Do not disable Gatekeeper globally.
Native app-access and macOS privacy permissions still require their own grants.
Test these permissions again after an upgrade; an ad hoc signature does not
provide a stable Apple-certified publisher identity across builds.

Developer ID signing and notarization can improve the installation experience,
but they are not prerequisites for distributing the CLI. The signed GitHub tag
and npm provenance described below authenticate the release separately from
Apple code signing.

## Signed release tag

After the release pull request merges, an authorized releaser creates a signed
annotated tag at that merged default-branch commit:

```sh
git tag -s vX.Y.Z -m "Satelle vX.Y.Z"
git push origin vX.Y.Z
```

The repository must have an active GitHub tag ruleset for `v*` that prevents
unauthorized creation, updates, deletion, and force pushes. The workflow rejects
an unsigned, lightweight, unverified, moved, version-mismatched, or wrong-target
tag with `release-tag-not-trusted` before public publication. Immutable releases
must also be enabled. The final publication step fails closed when that setting is
disabled, rechecks the signed tag at the publication boundary, and relies on the
authorized release writer not mutating the draft between the final asset read and
GitHub's immutable publication transition.

The publication API response must bind the same release ID and tag and report
`draft=false` and `immutable=true`. If it instead reports a public mutable
release, the workflow rechecks the signed tag, restores that exact release ID to
draft, validates the rollback response, and fails the release.
If the publication request fails without a response, the workflow reads that
exact release ID and retries the idempotent publication only while it remains a
mutable draft.
Draft restoration uses the same rule and retries only while that exact release
remains public and mutable.
Transient failures while re-reading the signed tag are retried inside the
bounded publication and restoration loops. A confirmed tag or source mismatch
still fails at once without another write.

The repository Actions secret `RELEASE_POLICY_TOKEN` must contain an authorized
releaser token with repository Administration read permission. The workflow uses
that token only to read the immutable-release policy before publication. Release
writes continue to use the job's scoped `GITHUB_TOKEN`.

## Local npm publication

The signed-tag workflow creates the draft GitHub release, publishes Cargo, and
signs each validated npm tarball with GitHub Actions provenance. The signing job
requires `contents: write` because GitHub only exposes draft releases to tokens
with push access; it rechecks the draft before signing. The final npm verification
job needs the same permission to download the draft package manifest.

The signing job uploads the
`npm-publication` Actions artifact containing all eight tarballs, their manifest,
and one Sigstore bundle per tarball. CI does not reserve npm versions or publish
npm packages.

Download that artifact from the successful signed-tag run. On the exact signed
source, validate the complete artifact set before the first registry write:

```sh
gh run download RUN_ID --name npm-publication --dir npm-publication
node npm/scripts/release.cjs validate-npm-artifacts npm-publication
```

Publish in manifest order using the maintainer's local npm credentials and the
`libnpmpublish` API bundled with that npm installation. Its `provenanceFile`
option accepts the matching CI-generated `.sigstore` file.

Do not combine CLI `--provenance=false` with `--provenance-file`: npm rejects
both options together, including when the first is false. These packages also
set `publishConfig.provenance`, so the CLI cannot select the supplied bundle
without conflicting with automatic provenance generation.

The publishing API accepts the existing tarball bytes without repacking them.
Load credentials through npm's configuration library and pass only the supplied
provenance file, not the automatic provenance option. Save this example as
`publish-local.cjs` beside the validated `npm-publication` directory and run
`node publish-local.cjs`:

```js
const fs = require('node:fs');
const path = require('node:path');
const { execFileSync } = require('node:child_process');
const npmRoot = path.join(execFileSync('npm', ['root', '-g'], {
  encoding: 'utf8',
}).trim(), 'npm');
const Config = require(path.join(npmRoot, 'node_modules/@npmcli/config'));
const { definitions, shorthands, flatten } = require(path.join(
  npmRoot, 'node_modules/@npmcli/config/lib/definitions',
));
const { publish } = require(path.join(npmRoot, 'node_modules/libnpmpublish'));
const pacote = require(path.join(npmRoot, 'node_modules/pacote'));
const npmFetch = require(path.join(npmRoot, 'node_modules/npm-registry-fetch'));
const npa = require(path.join(npmRoot, 'node_modules/npm-package-arg'));
const assert = require('node:assert/strict');

async function main() {
  const config = new Config({
    npmPath: npmRoot, definitions, shorthands, flatten, argv: [],
  });
  await config.load();
  if (!config.validate()) throw new Error('Invalid local npm configuration');
  const options = {
    ...config.flat, access: 'public', defaultTag: 'latest', preferOnline: true,
  };
  delete options.provenance;
  const directory = path.resolve('npm-publication');
  const artifacts = JSON.parse(fs.readFileSync(
    path.join(directory, 'npm-artifacts.json'), 'utf8',
  ));
  // Check every destination before the first registry write.
  for (const entry of artifacts.packages) {
    const spec = npa.resolve(entry.package, entry.version);
    assert.equal(npmFetch.pickRegistry(spec, options), 'https://registry.npmjs.org/');
  }
  for (const entry of artifacts.packages) {
    const spec = npa.resolve(entry.package, entry.version);
    const endpoint = `${spec.escapedName}/${entry.version}`;
    let existing;
    try {
      existing = await npmFetch.json(endpoint, options);
    } catch (error) {
      if (error.code !== 'E404') throw error;
    }
    if (existing) {
      assert.equal(existing.dist.integrity, entry.integrity);
      continue;
    }
    const artifact = path.join(directory, entry.file);
    const manifest = await pacote.manifest(artifact, {
      fullmetadata: true, fullReadJson: true,
    });
    await publish(manifest, fs.readFileSync(artifact), {
      ...options, provenanceFile: `${artifact}.sigstore`,
    });
    console.log(`Submitted ${entry.package}@${entry.version}; verify public integrity before finalization`);
  }
}
main().catch(error => {
  console.error({ code: error.code, message: error.message });
  process.exitCode = 1;
});
```

The supplied file retains the signature created by the signed-tag CI run. npm
verifies its signature, package identity, and tarball digest before submission.
A successful submission is not proof of public availability: read each exact
version from the registry and compare its integrity with the artifact manifest
before finalizing the release. npm can return HTTP 202 while processing a
submission, then return 404 for a public read and a staged-version conflict on
an immediate repeat submission. Preserve the successful submission record and
poll public availability instead of submitting that version again. Once all
versions are visible, verify every integrity and provenance attestation before
finalization. If visibility does not converge, keep the release as a draft and
preserve the registry responses for investigation. `npm stage list --json` can
inspect approval-pending versions with an npm version that supports staging;
absence from that list does not prove a recent submission failed.

The maintainer token must allow package writes. Unattended publication also
requires the account and package policies to permit that token without 2FA.
Never copy the token to CI or commit it.

On retry, skip an already published version only after its registry integrity
matches the manifest. A mismatch stops publication. Do not rebuild the tarballs.

## Post-publication finalization

After all eight packages are public, dispatch `release.yml` from the default
branch with operation `finalize` and the release version. It verifies the signed
tag, release pull request, and all eight registry integrities. It verifies each
provenance signature against the release workflow identity and checks the signed
repository, tag, source commit, package identity, and tarball digest.
Six native runners install both launcher identities with npm, pnpm, and Bun,
run `satelle --version` and `satelle paths --json`, and audit npm signatures.

The final job loads the validated artifact bundle from the successful signed-tag
run, checks the exact draft asset set, and publishes the immutable GitHub release.
Cargo publication and every native validation lane must pass first.

## External release gates

- The `v*` tag ruleset must be active. Immutable releases are enabled for the repository.
- The security and legal language review covers remote control, provider
  credentials, diagnostics, and user consent.
- `CARGO_REGISTRY_TOKEN` must be scoped to publishing Satelle.
- Local npm credentials must have write access to all eight package identities.
- The signed-tag run must create valid npm provenance bundles.
- Registry integrity, provenance, and six-platform validation must pass before
  finalizing the GitHub release.

---
title: Release process
description: Prepare, validate, publish, and audit a Satelle release.
---

Satelle releases start with a reviewed release pull request and finish only
after the tag workflow validates the whole binary and npm package graph. A
pull request merge never publishes packages or creates a final GitHub release.

## Release tooling boundaries

[Tegami](https://tegami.fuma-nama.dev/getting-started) 1.2.5 is the preferred
changelog and versioning tool. It runs on Node.js 24 as isolated repository
tooling under `npm/release-tooling`; neither Tegami nor Node.js is a runtime
dependency of the Rust CLI or Host Daemon.

Run the non-mutating validation before preparing a release:

```sh
npm ci --prefix npm/release-tooling --ignore-scripts
npm run dry-run --prefix npm/release-tooling
```

The report records the Node.js and Tegami versions, Cargo package discovery,
the temporary fixture's generated files, version and dependency updates, and
the registry targets skipped by the dry run. The Cargo plugin is configured to
avoid a duplicate dependent bump because all Satelle crates inherit one shared
workspace version. Cargo package discovery and version updates stay enabled,
while crates.io publication is disabled for MVP.
Satelle does not publish a crates.io crate.

On the normal path, the release workflow runs Tegami's publication plan after
the dry run passes. Tegami keeps crates.io disabled, then `release.yml` acts as
the explicit hook that builds, signs, and publishes the binary and npm graph.
This keeps the recoverable npm transaction outside Tegami without bypassing
Tegami's changelog and version plan.

If Tegami validation fails, the release pull request can select the manual release
fallback by adding `npm/release-tooling/manual-release.json`. The reviewed file
must use schema `satelle.manual-release-fallback.v1` and match the release
version. It must also set `generatedChangesReviewed` to `true`, give a nonempty
`reason`, and list the
committed versioned Cargo `CHANGELOG.md` files. The tag workflow validates that
record and those files before it uses the same signed artifact publication
hook. Without that reviewed record, a Tegami failure stops publication.

## Release pull request

The release pull request must contain one reviewed version everywhere the
release contract requires it: Rust workspace metadata, all eight npm package
manifests, exact launcher dependency ranges, lockfiles, and Tegami changelog
output. At least one committed Cargo package `CHANGELOG.md` must contain a
heading for that exact version. Run the repository release checks without
publishing:

```sh
node npm/scripts/release.cjs check
npm test
```

The GitHub Actions pull request run builds all six Controller targets, packs
all eight npm packages, validates native binary formats and archive roots,
compares archive and npm executable digests, creates `SHA256SUMS`, runs npm
publish dry runs, and exercises install, upgrade, smoke, and uninstall paths.

## Signed release tag

After the release pull request merges, an authorized releaser creates a signed
annotated tag at that merged default-branch commit:

```sh
git tag -s vX.Y.Z -m "Satelle vX.Y.Z"
git push origin vX.Y.Z
```

The repository must have an active GitHub tag ruleset for `v*` that prevents
unauthorized creation, updates, deletion, and force pushes. The workflow rejects
an unsigned, lightweight, unverified, moved, version-mismatched, or wrong-target
tag with `release-tag-not-trusted` before public publication. Immutable releases
must also be enabled. The final publication step fails closed when that setting is
disabled, rechecks the signed tag at the publication boundary, and relies on the
authorized release writer not mutating the draft between the final asset read and
GitHub's immutable publication transition.

The publication API response must bind the same release ID and tag and report
`draft=false` and `immutable=true`. If it instead reports a public mutable
release, the workflow rechecks the signed tag, restores that exact release ID to
draft, validates the rollback response, and fails the release.
If the publication request fails without a response, the workflow reads that
exact release ID and retries the idempotent publication only while it remains a
mutable draft.
Draft restoration uses the same rule and retries only while that exact release
remains public and mutable.
Transient failures while re-reading the signed tag are retried inside the
bounded publication and restoration loops. A confirmed tag or source mismatch
still fails at once without another write.

The repository Actions secret `RELEASE_POLICY_TOKEN` must contain an authorized
releaser token with repository Administration read permission. The workflow uses
that token only to read the immutable-release policy before publication. Release
writes continue to use the job's scoped `GITHUB_TOKEN`.

## Candidate publication and validation

The tag workflow creates a draft GitHub release only after six archives pass
validation and GitHub has produced and verified their Sigstore-backed artifact
attestations. It publishes npm packages through
[npm trusted publishing](https://docs.npmjs.com/trusted-publishers/) in this
order:

1. Six platform-native packages.
2. `@microck/satelle`.
3. `satelle`.

Every package first uses the non-default `rc-vX.Y.Z` tag. The workflow records
each immutable publication outside the runner. A retry verifies the registry
version and integrity against `npm-artifacts.json`; it never republishes
different bytes under an existing version and never moves the signed tag. If
an immutable version exists without its candidate tag, publication fails with
`candidate-registry-tag-mismatch` instead of exposing the dist-tag token to the
OIDC publishing step.

All six Controller runners then clean-install both launcher identities with
npm, pnpm, and Bun. Each installation must pass `satelle --version` and
`satelle paths --json` before promotion starts. The GitHub release remains
draft throughout candidate publication and validation.

## Latest promotion

npm OIDC currently authorizes package publication but not `npm dist-tag`.
Configure `NPM_DIST_TAG_TOKEN` as a narrowly scoped release secret that can
change dist-tags for the eight Satelle package identities. Do not grant it
package publication rights beyond what npm requires for dist-tag maintenance.
Issue it to a dedicated npm automation identity, keep that credential only in
the GitHub Actions secret, and do not use that identity for interactive npm
maintenance.
Configure `NPM_PROMOTION_RECORD_KEY` as a separate stable random secret for
checkpoint authentication. Do not reuse the npm token as this key.

The workflow snapshots every prior `latest` value into an append-only promotion
checkpoint before changing any tag. Draft asset validation permits only the
validated base assets and typed candidate or promotion checkpoint names, so a
retry can load its prior state. One non-cancelling repository-wide
concurrency group serializes promotion and rollback across all versions. After
each package, a new checkpoint is attached to the draft release.

Every checkpoint is authenticated with a domain-separated HMAC derived from
the dedicated checkpoint key. A retry verifies that authentication
and requires the exact dependency-ordered package graph from the signed release
source before accepting the record. Replacing a draft-release asset therefore
fails before any npm command can use its package names or prior tag values. Do
not rotate `NPM_PROMOTION_RECORD_KEY` while any draft release retains promotion
checkpoints. An emergency rotation intentionally makes those checkpoints fail
closed and requires manual recovery. Rotating `NPM_DIST_TAG_TOKEN` does not
invalidate checkpoint authentication.

A retry re-reads npm. It accepts only the recorded prior state as pending or
the candidate version as complete. Any other value raises
`promotion-state-conflict` and is not overwritten. Immediately before
every promotion write, the workflow also requires the GitHub release to remain
draft. Immediately before completion, it re-reads all eight `latest` tags and
requires every one to equal the candidate. It repeats that full read even when
recovery loads an already complete record. Only then does it publish the GitHub
release.

npm does not expose a supported conditional dist-tag update. Before each
promotion or rollback write, Satelle therefore authenticates the maintenance
token with `npm whoami` and requires `npm access list collaborators` to show
that identity as the target package's only read-write collaborator. Any other
writer fails with `promotion-writer-access-conflict` before the tag write.
Read-only collaborators do not block release. The signed tag object and peeled
source commit are also rechecked before each promotion write and again in the
same step that makes the GitHub release public.

## Candidate tag recovery

Recovery must be dispatched from the current default-branch head. Before either
recovery job checks out code or receives the npm maintenance token, the workflow
resolves the annotated tag, verifies its GitHub signature, default-branch
ancestry, and merged release pull request, then checks out the verified commit
digest. Immediately before every candidate dist-tag write, it rechecks the tag
object, peeled source commit, and draft release state so moved tags and published
releases fail closed.

If an immutable candidate exists without `rc-vX.Y.Z`, dispatch the Release
workflow with operation `candidate-tag-repair` and the existing `X.Y.Z`
version. The recovery job checks out the matching signed tag, requires the
GitHub release to remain draft, verifies each existing package against the
validated integrity manifest, and repairs only missing candidate tags. Rerun
the signed-tag workflow after recovery to resume publication and validation. A
candidate tag that already points to another version is a conflict: recovery
does not overwrite it, and the GitHub release remains draft.

## Promotion rollback

If promotion must be aborted while the GitHub release is still draft, dispatch
the Release workflow with operation `rollback` and the existing `X.Y.Z`
version. Recovery loads the latest durable checkpoint and restores tags in
reverse dependency order. It removes `latest` when the checkpoint says the tag
was previously absent.

Rollback retries treat the candidate value as pending, the prior value as
complete, and every other value as a conflict. A rolled-back, incomplete,
conflicted, or rollback-mode record never permits the GitHub release to leave
draft state. Rollback scans promotion records across every draft GitHub release and
refuses to start while another version is nonterminal. Immediately before each
restoration write, recovery revalidates the signed tag object, peeled source
commit, and draft release state. Recovery does not move the signed tag or
republish package bytes.

## External release gates

Repository code cannot prove account and platform state. Before the first
public release, an authorized maintainer must verify all of these outside the
checkout:

- The `v*` GitHub tag ruleset is active.
- Immutable releases are enabled for the repository.
- Each npm package identity exists and trusts `release.yml` for OIDC publish.
- `NPM_DIST_TAG_TOKEN` has the minimum working dist-tag scope.
- The token identity is the sole read-write collaborator on all eight npm
  packages; human and team access is read-only during promotion and recovery.
- `NPM_PROMOTION_RECORD_KEY` contains a separate stable random value.
- The security and legal language review covers remote desktop control, YOLO,
  diagnostics, provider credentials, and user consent.
- A real tag run produces and verifies attestations, publishes all candidates,
  passes six-platform registry validation, promotes all tags, and publishes the
  GitHub release.

## Check the local context

```sh
satelle config check --json
satelle config explain --host local-demo --json
satelle paths --json
```

Use the paths report instead of assuming an operating-system-specific config
location.

Local daemon and SSH-tunnel connections always bypass environment proxies.
Proxy settings still apply to public release downloads and direct HTTPS Hosts.

## Build a setup plan

For an agent-safe plan that never prompts:

```sh
satelle setup --host local-demo --dry-run --no-input --json
```

Limit the plan when you are addressing one subsystem:

```sh
satelle setup --host local-demo --component desktop --dry-run --json
satelle setup --host local-demo --component provider-auth --dry-run --no-input --json
```

Supported component values are `transport`, `host`, `codex`, `computer-use`,
`desktop`, `provider-auth`, and `all`.

## Choose how the Host runs

Pass exactly one lifecycle mode when the default is not suitable:

```sh
satelle setup --host local-demo --on-demand --dry-run
satelle setup --host local-demo --persistent --dry-run
```

Local setup is planning-only. SSH setup applies the authenticated transport
handoff described in the remote connection guide. On macOS and Windows,
persistent mode also installs or updates a user-scoped login-session service.
Linux does not support a persistent service: an explicit persistent request
fails closed, while an inherited persistent default falls back to on-demand
mode and reports the fallback. Desktop and provider setup run through the
authenticated Host after the daemon is ready; the SSH bootstrap does not apply
those broader components directly.

When setup includes the Host component and the running SSH Host uses an
incompatible protocol, the plan reports `update_protocol_incompatible`, including
when its version is older. Setup upgrades that daemon before sending authenticated
cache, desktop, or provider requests. Selecting only `desktop` or `provider-auth`
does not upgrade the Host and can stop on a protocol error. Select `--component
host` to upgrade first, or `--component all` to include the follow-up setup.

On Windows, persistent mode registers a per-user Task Scheduler logon task
for the bootstrap OS account with an interactive-token principal, so the
daemon runs inside the operator's desktop session with least privilege. An
interactive session must exist: the task does not start when nobody is logged
on. Do not reconfigure the task to run whether or not a user is logged on,
and do not install the daemon as a Session 0 Windows Service. Without an
interactive desktop, screen capture and input injection fail. Setup reads the
registered task definition back on later runs and rejects anything that is
not the expected interactive-token logon task.

## Bind the visible desktop

User configuration can set `desktop_user` and either a preference or a native
selector. Do not set both a preference and a native selector for the same
Host.

```toml
[hosts.local-demo]
transport = "local"
adapter = "codex"

[hosts.local-demo.desktop_bindings.operator]
desktop_user = "operator"
desktop_session_preference = "console"
```

Use `only` instead of `console` only when setup must fail rather than select
another eligible session.

Managed daemons, including SSH bootstrap and persistent services, read these
bindings from the Host user's `hosts.local-demo` configuration. Project config
and the Controller's default Host do not select the daemon's desktop. Service
storage paths and launch policies remain controlled by the managed launch.

## Configure provider authentication

Store a Secret Source descriptor in user configuration. Do not put the secret
value itself in the TOML file or command line.

```toml
[hosts.local-demo.desktop_bindings.operator.provider_auth.openai]
kind = "environment"
variable = "OPENAI_API_KEY"
```

File, operating-system credential-store, and Host-store descriptors are also
supported. See [Provider authentication](/docs/reference/provider-auth).

## Verify the Host

```sh
satelle doctor --host local-demo --scope computer-use --refresh --json
satelle host sessions --host local-demo --json
satelle host status --host local-demo --json
```

`ready` means the live action-path probe succeeded on this Host. A binary,
plugin, or feature flag alone is not proof of readiness.

## Recover an interrupted setup begin

Windows bootstrap metadata and execution markers use explicit protected file
permissions owned by the signed-in account, including when SSH runs elevated.
The private directory's inherited permissions alone do not establish file
ownership. File security is set at creation, without repeated ACL updates on
heartbeat writes.

An interrupted SSH setup can leave an execution-started bootstrap claim even
when its maintenance ledger has no remaining recovery work. Recovery must hold the Host's
exclusive storage ownership lock, match its pinned identity and the exact stale
claim, and confirm that the operation has no setup ledger entry. A missing entry
in a public history summary is insufficient.

The owner-local recovery operation archives the complete claim with a durable
ledger-absence receipt. A missing run can also mean retention removed a known
terminal outcome; recovery does not claim that the operation never ran.
Running and outcome-unknown ledger entries cannot expire and prevent archival.
Recovery never deletes the claim evidence, resets the Host store,
changes credentials, or treats another mutation phase as an uncommitted begin.
A live owner, recent heartbeat, existing ledger run, unexpected execution marker,
or changed claim stops recovery before archival. Re-run normal setup only after
this exact recovery succeeds.

## Inspect a stalled native runtime admission

```sh
satelle host start --foreground --error-format human --log-verbosity debug
```

Admission logs identify path resolution, receipt reads, metadata validation,
directory checks, and binary verification. They do not print credentials,
receipt contents, or filesystem paths. The last stage identifies the operation
to investigate; it does not prove the cause of a stall.

Windows interactive Host and bootstrap tasks run at normal scheduling priority.
Runtime identity checks still hash the installed binary before native execution;
they do not inherit Task Scheduler's default background priority.

Windows background bootstrap helpers, SSH helpers, updater checks, telemetry
delivery, batch commands and managed provider processes do not open terminal
windows. The persistent task launches a hidden PowerShell owner that
waits for its no-console Host Daemon and returns its exit status. Task Scheduler
still tracks the daemon lifetime. CLI output and private diagnostics remain
available; app-access and operating-system approval prompts remain visible.
